# Decision states

Exactly one of these ends every idea grilling. The state is a claim about evidence, not about enthusiasm.

## PROCEED

The idea survived grilling, and no open assumption could kill it.

Requires: a named first user, a problem stated in that user's words, and a reason this is worth doing rather than the nearest alternative.

Next: `project-brief`.

## REFINE

The idea survived, but something load-bearing is still unresolved — the user, the problem, the scope, or an assumption that research can settle.

Requires: naming what specifically is unresolved. "Needs more thought" is not a REFINE; it is an unfinished grilling.

Next: `idea-research` if the gap is factual, another grilling round if the gap is conceptual.

## PARK

The idea is sound but blocked on something outside the decision — time, a dependency, a market that does not exist yet.

Requires: the blocking condition, written as an observable trigger. "When the API ships public write access", not "later".

Next: nothing. The record is the deliverable. It gets revisited when the trigger fires.

## REJECT

Grilling found the thing that kills it.

Requires: the specific killer, in one sentence. A REJECT with no stated killer is a PARK wearing the wrong label.

Next: nothing. Write it down anyway — a rejected idea is the cheapest way to avoid rediscovering the same dead end.

## Choosing

Reach for the state the evidence supports. The pull is always toward PROCEED, because the user brought the idea and wants it to live; that pull is the reason this file exists.

Two honest tests:

- Could you defend this state to someone who wants the idea dead?
- Could you defend it to someone who wants it built?

A state that fails either test is the wrong state.
